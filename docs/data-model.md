# Data model

Entities follow specification §9. The two structural decisions that matter:

**`Source` ↔ `Place` is many-to-many.** One video mentions three places; one
place accumulates five sources over months. `SourcePlaceEvidence` is the join,
and it carries *why* — the takeaway, the verbatim quote and the media timestamp.

**`Place` is canonical; `TripPlace` is personal.** `Place` holds identity:
coordinates, provider IDs, aliases, address. `TripPlace` holds the traveller's
relationship to it: status, why it was saved, notes, favourite, rating, visits.
Enrichment writes only to `Place` and `PlaceFact`. Nothing enrichment does can
overwrite what the traveller wrote.

```
User ─┬─ Trip ─┬─ Destination ──┐
      │        ├─ Source ───────┼── SourcePlaceEvidence ── Place ── PlaceFact
      │        │      └─ ExtractionCandidate                 │
      │        ├─ KnowledgeItem ─────────────────────────────┤
      │        ├─ TripPlace ────────────────────────────────┘
      │        │      ├─ Visit
      │        │      └─ Collection (many-to-many)
      │        ├─ ItineraryItem · Booking · Expense · Document
      │        └─ AgentRun · SyncOperation
      └─ AuditEvent
```

## Notable columns

| Table | Column | Why it exists |
| --- | --- | --- |
| `source` | `fingerprint` | Content hash; a retried batch import cannot duplicate |
| `source` | `status`, `failure_reason`, `attempts` | The recoverable-failure path required by §12 |
| `extraction_candidate` | `evidence_json` | The quote behind the claim, shown on the review screen |
| `extraction_candidate` | `is_place_candidate` | A stay *tip* has no location — it is knowledge, not a pin |
| `extraction_candidate` | `duplicate_of_place_id` | Surfaced for the user; never auto-merged |
| `trip_place` | `reason_saved` | The product's core differentiator; user-owned |
| `trip_place` | `needs_review` | A quality flag, not a lifecycle status |
| `place_fact` | `provenance`, `checked_at`, `expires_at` | Freshness and the source hierarchy |
| `knowledge_item` | `requires_official_verification` | Border and visa advice can never be creator-sourced |
| `knowledge_item` | `user_edited` | Marks a record enrichment must leave alone |
| `expense` | `amount_base` | Converted at capture time, so history is stable |
| `sync_operation` | `client_op_id` | Idempotency key for a replayed offline queue |

## Lifecycle

`inbox → saved → must_visit → planned → visited`, plus `archived`. Per §7.2,
`booked` is *derived* from an active reservation, `favourite` is an independent
flag and `needs_review` is a data-quality flag — none of them are statuses.

## Schema management

`Base.metadata.create_all()` bootstraps the schema, which is deliberate for a
single-user prototype. Alembic is the documented follow-up before the schema is
deployed anywhere shared; the models are already written so that a first
autogenerated revision is a faithful baseline.
